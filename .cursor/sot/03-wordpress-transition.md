# 워드프레스 전환 시 변경 지침

> **채택:** 2026-08-03 · 기본 트랙 = WordPress (`_docs/active-track.md`)  
> UI·UX·반응형·접근성·콘텐츠 디자인·비주얼 QA는 `.cursor/rules/25-uiux-design-director.mdc` / `.cursor/sot/01-project-context` 원칙을 **유지**하고, 아래는 CMS·테마 구현에서 **우선 적용**한다.  
> (디렉터 SoT 우선순위: CONTEXT·토큰·do-dont·본 문서·`70`이 Director보다 위)

이 문서는 Design Director 전체 내용을 대체하지 않는다. 하드코딩 사이트에서 워드프레스 기반 사이트로 바뀌면서 달라지는 항목만 우선 적용한다.

## 1. 구현 전제 변경

- 결과물은 정적 사이트나 독립형 프런트엔드가 아니라 `워드프레스 커스텀 테마`로 구현한다.
- 디자인과 화면 구조는 Cursor가 HTML, CSS, JavaScript, PHP로 직접 구현한다.
- Elementor 등 페이지 빌더는 기획서에서 요구하거나 고객 편집 범위상 명확한 이점이 있을 때만 사용한다. 임의로 도입하지 않는다.
- 워드프레스가 제공하는 관리자, 사용자 권한, 글, 페이지, 미디어, 메뉴, 데이터베이스 기능을 다시 개발하지 않는다.
- PHP와 MySQL을 지원하는 워드프레스 호스팅을 전제로 개발·배포한다. 정적 호스팅만 가능한 환경을 선택하지 않는다.

## 2. 작업 시작 시 추가로 확정할 내용

기존 기획 해석 항목에 다음 내용을 추가한다.

```text
워드프레스 구현 방식: 커스텀 클래식 테마 / 커스텀 블록 테마 / 기존 테마 확장
고객이 관리자에서 수정할 항목:
수정하지 못하게 고정할 구조:
콘텐츠 유형: 페이지 / 글 / 커스텀 게시물 유형
분류 체계: 카테고리 / 태그 / 커스텀 택소노미
필요한 입력 필드와 반복 항목:
사용자 역할과 권한:
사용 플러그인과 도입 이유:
문의 데이터의 저장·전송 위치:
호스팅·도메인·메일 발송 환경:
백업·업데이트 책임 주체:
```

고객이 무엇을 수정할지 확정하지 않은 상태에서 화면부터 전부 하드코딩하지 않는다.

## 3. 콘텐츠 구조 변경

- 고객이 반복해서 추가하는 공지, 소식, 시공 사례, 포트폴리오, 자료는 정적 HTML 배열로 넣지 않는다.
- 일반 문서는 `페이지`, 시간순 소식은 기본 `글`, 고유한 필드와 목록·상세 구조가 필요한 콘텐츠는 `커스텀 게시물 유형`으로 설계한다.
- 커스텀 게시물 유형, 택소노미, 업무 규칙처럼 테마가 바뀌어도 남아야 하는 기능은 테마에 종속시키지 않고 사이트 전용 플러그인으로 분리한다.
- 테마는 콘텐츠의 표시 방식과 레이아웃을 담당한다. 사이트의 핵심 데이터 구조와 운영 기능을 `functions.php`에 무작정 몰아넣지 않는다.
- 제목, 본문, 대표 이미지, 요약, 날짜 등 워드프레스 기본 필드로 충분하면 별도 필드를 만들지 않는다.
- 별도 필드는 실제 운영자가 이해할 수 있는 이름, 설명, 입력 형식, 필수 여부를 갖춰야 한다.
- 고객이 바꾸어야 하는 연락처, 주소, 영업시간, CTA 문구, 대표 이미지 등을 코드 여러 곳에 중복 하드코딩하지 않는다.
- 편집 가능한 영역은 실제 콘텐츠 변화가 디자인을 망가뜨리지 않도록 최소·평균·최대 길이, 이미지 없음, 항목 0개·1개·다수 상태를 검증한다.

## 4. 템플릿 구현 변경

- 워드프레스 템플릿 계층과 루프를 사용해 홈, 일반 페이지, 글 목록, 상세, 검색, 404, 커스텀 게시물 목록·상세를 연결한다.
- 같은 헤더, 푸터, 내비게이션, 카드, 목록을 페이지마다 복제하지 않는다.
- 활성 메뉴, 페이지 제목, 대표 이미지, 글 상태, 페이지네이션과 검색 결과는 실제 워드프레스 데이터로 동작하게 한다.
- 내부 링크와 자산 경로에 개발용 도메인이나 절대 로컬 경로를 하드코딩하지 않는다. 워드프레스 URL·테마·플러그인 API를 사용한다.
- CSS와 JavaScript는 워드프레스의 enqueue 방식으로 불러오고, 필요한 화면에서만 로드한다.
- 이미지 출력은 미디어 라이브러리와 워드프레스 이미지 함수를 우선 사용해 대체 텍스트, 반응형 이미지, 크기 선택이 유지되게 한다.
- 직접 SQL을 작성하기보다 워드프레스 쿼리 API를 우선 사용한다. 직접 쿼리가 불가피하면 이유를 남기고 안전한 준비 쿼리를 사용한다.

## 5. 관리자 UX와 권한 변경

- 고객의 일상 운영 계정에는 필요한 최소 권한만 부여한다. 글·사례 관리만 필요하다면 전체 관리자 권한을 기본값으로 주지 않는다.
- 관리자 화면에는 고객이 실제로 수정할 메뉴와 필드만 노출한다. 개발자용 설정과 사이트 구조 변경 권한을 불필요하게 열어두지 않는다.
- 입력 필드 이름은 코드 용어가 아니라 고객의 업무 용어를 사용한다.
- 필드별 권장 이미지 비율, 글자 수, 입력 예시와 필수 여부를 안내한다.
- 관리자가 잘못된 콘텐츠를 입력해도 공개 화면이 깨지지 않도록 누락값, 긴 제목, 잘못된 이미지 비율과 빈 목록의 대체 상태를 구현한다.
- 고객이 직접 수정할 수 있다는 사실과 레이아웃까지 자유롭게 바꿀 수 있다는 사실을 구분한다. 합의되지 않은 전체 페이지 편집 권한은 제공하지 않는다.

## 6. 플러그인 선택 규칙 추가

- 워드프레스 기본 기능으로 충분하면 플러그인을 추가하지 않는다.
- 플러그인은 필요한 기능, 최근 유지관리 상태, 현재 워드프레스·PHP 호환성, 보안 이력, 라이선스, 유료 갱신비, 데이터 이동 가능성을 확인한 뒤 선택한다.
- 비슷한 역할의 플러그인을 중복 설치하지 않는다.
- 단순한 화면 효과나 몇 줄의 표현을 위해 대형 플러그인을 도입하지 않는다.
- 플러그인을 설치하기 전에 제거했을 때 사라지는 기능과 데이터, 테마 변경 시 영향, 고객이 부담할 연간 비용을 기록한다.
- 플러그인 수 자체를 품질 기준으로 삼지 않는다. 실제 의존성, 성능, 업데이트 책임과 충돌 위험을 기준으로 판단한다.

## 7. 보안 규칙 변경

- 모든 입력값은 용도에 맞게 검증하고 정리하며, 출력 시 HTML·속성·URL·JavaScript 문맥에 맞게 escape한다.
- 관리자 작업, 폼 처리, AJAX·REST 요청에는 해당 작업의 권한 확인과 nonce 검증을 적용한다. nonce만으로 로그인이나 권한 검사를 대신하지 않는다.
- 비밀키, SMTP 비밀번호, 외부 API 키를 테마 파일이나 브라우저 JavaScript에 넣지 않는다.
- 파일 업로드는 허용 형식, 용량, 권한과 저장 위치를 제한한다.
- 테마·플러그인·워드프레스 코어를 임의 수정하지 않는다. 수정 코드는 커스텀 테마, 자식 테마 또는 사이트 전용 플러그인에 둔다.
- 사용하지 않는 테마·플러그인·계정과 공개 엔드포인트를 그대로 방치하지 않는다.
- 보안 플러그인 설치만으로 보안 검수가 끝났다고 판단하지 않는다.

## 8. 문의 폼 변경

- 문의 폼은 화면만 만들지 말고 서버 측 검증, 스팸 방지, 전송 성공·실패·중복 전송 상태까지 확인한다.
- 이메일 발송만 할지 워드프레스 DB에도 저장할지 먼저 정한다. 필요하지 않은 개인정보는 저장하지 않는다.
- 저장한다면 수집 항목, 목적, 보유 기간, 삭제 방식, 열람 권한과 개인정보 동의 문구를 기획서에 반영한다.
- SMTP 또는 호스팅 메일 환경에서 실제 수신을 확인한다. 개발 환경의 성공 메시지만 보고 납품 완료로 처리하지 않는다.
- 관리자 알림 메일과 사용자 자동회신에는 제출된 민감정보를 불필요하게 반복하지 않는다.
- 공개 폼에는 CAPTCHA, 허니팟, 속도 제한 등 프로젝트에 맞는 스팸 방지 수단을 적용한다.

## 9. 성능·SEO 변경

- 워드프레스 코어, 테마, 플러그인이 함께 만드는 최종 페이지를 기준으로 성능을 측정한다.
- 실제로 사용하지 않는 플러그인 자산이 전체 페이지에 로드되는지 확인하고 가능한 범위에서 제거한다.
- 반복 목록은 무제한 출력하지 않고 페이지네이션 또는 합리적인 개수 제한을 사용한다.
- 캐시 플러그인 적용 전후를 구분하고, 캐시가 없어도 구조적으로 과도한 쿼리와 대형 자산이 없는지 확인한다.
- 사이트 제목, 설명, 고유주소, 검색 노출 설정, 사이트맵, canonical, Open Graph는 설치된 SEO 도구와 중복 생성하지 않는다.
- 개발·스테이징의 `검색 엔진 접근 차단` 설정이 운영 배포 후 남아 있지 않은지 확인한다.

## 10. 워드프레스 전용 QA 추가

기존 브라우저·반응형·접근성 QA에 다음을 추가한다.

```text
홈·일반 페이지·글 목록·글 상세·검색·404 확인
커스텀 게시물 목록·상세·분류·페이지네이션 확인
로그인·비로그인·편집자 권한별 노출과 접근 확인
관리자 바가 표시될 때 헤더·고정 요소 충돌 확인
초안·비공개·예약·대표 이미지 없음 상태 확인
메뉴 추가·삭제·다단계 메뉴와 모바일 메뉴 확인
관리자에서 수정한 내용이 공개 화면에 정확히 반영되는지 확인
캐시 사용 시 수정 내용 갱신과 폼·로그인 예외 확인
플러그인 비활성화 또는 오류 시 핵심 화면의 실패 방식 확인
콘솔 오류, PHP 오류 로그, 404 자산, 느린 쿼리 확인
```

관리자 화면에서 직접 콘텐츠를 추가·수정·삭제해보지 않았다면 CMS 연동 검수를 완료했다고 말하지 않는다.

## 11. 배포·납품 변경

- 운영 서버에 올리기 전 파일과 데이터베이스를 함께 백업한다.
- 로컬·스테이징·운영 사이에서 도메인, 사이트 URL, 고유주소, 업로드 경로와 직렬화 데이터를 안전하게 이전한다.
- 운영 환경의 PHP·MySQL 버전, HTTPS, 파일 권한, 메일 발송, 업로드 제한과 예약 작업을 확인한다.
- 고객 명의의 도메인·호스팅을 기본으로 하고, 주계정 비밀번호 공유 대신 별도 작업 계정과 필요한 권한을 사용한다.
- 납품 시 테마, 사이트 전용 플러그인, 사용 플러그인과 라이선스, 관리자 역할, 백업·복구 방법, 업데이트 방법을 문서화한다.
- 고객에게 글·이미지 추가, 수정, 삭제와 대표 이미지 설정 방법을 실제 화면 기준으로 안내한다.
- 자동 업데이트 여부와 장애 발생 시 책임 범위를 합의하지 않은 채 활성화하지 않는다.
- 납품 직전 코어·테마·플러그인을 무조건 최신화하지 않는다. 먼저 백업하고 스테이징에서 호환성을 확인한 뒤 반영한다.

## 12. 제작 벤치마크 변경

기존 제작시간 기록에 다음 단계를 별도로 추가한다.

```text
워드프레스 설치·개발환경 구성 시간
테마 구조 설계 시간
콘텐츠 유형·필드·권한 설계 시간
정적 화면을 동적 템플릿으로 연결한 시간
관리자 입력 UX 구성 시간
플러그인 조사·설정·충돌 해결 시간
문의 폼 실제 발송·스팸 방지 검수 시간
스테이징·운영 이전과 도메인 연결 시간
백업·보안·업데이트 검수 시간
고객용 관리자 사용 안내 작성 시간
```

정적 화면이 완성된 시점과 고객이 관리자에서 실제 운영 가능한 시점을 구분해 기록한다.

## 13. 초기 제공 범위 변경

초기 워드프레스 제작 실험의 기본 범위는 다음으로 제한한다.

```text
맞춤형 반응형 소개 홈페이지
관리자 작성형 공지·소식 또는 포트폴리오 1종
목록·상세·분류 또는 페이지네이션
문의 폼
편집자 계정과 간단한 운영 안내
```

다음 기능은 기본 범위로 자동 포함하지 않는다.

```text
방문자 글쓰기 게시판
회원가입·마이페이지·소셜 로그인
비밀글·댓글·신고·관리자 승인
결제·예약·구독·환불
다국어·다중 사이트
```
